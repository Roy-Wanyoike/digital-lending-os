    26→## 1. Executive Summary
    27→
    28→### 1.1 Vision
    29→
    30→Youngsend is a multi-tenant B2B fintech platform providing escrow-based payments, digital wallets, trust scoring, and compliance services across emerging markets (Nigeria, Kenya, South Africa, and broader Africa). This architecture redesign transforms the platform from a monolithic SQLite-backed application into a fully cloud-native, event-driven system capable of serving **100 million users** with **near-zero downtime** (target: 99.99% availability).
    31→
    32→The redesign leverages React Server Components (RSC) and Next.js App Router as the Backend-for-Frontend (BFF), Kafka as the event backbone, PostgreSQL as the primary relational store, and Cloudflare's global edge network for CDN caching, bot protection, and JWT validation. Every domain is modeled as a bounded context with its own Kafka topic namespace, enabling independent scaling and deployment.
    33→
    34→### 1.2 Key Architectural Decisions
    35→
    36→| Decision | Rationale |
    37→|----------|-----------|
    38→| Next.js App Router as BFF | RSC eliminates the need for a separate API layer for page rendering; streaming SSR provides sub-200ms TTFB; unified deployment reduces operational complexity |
    39→| Kafka for async communication | Loose coupling between services; exactly-once semantics for financial transactions; natural audit log via immutable events |
    40→| PostgreSQL with Patroni HA | Financial data requires ACID guarantees; Row Level Security enforces multi-tenant isolation at the database level; mature tooling and ecosystem |
    41→| Cloudflare Edge as L1 cache | 300+ PoPs globally; sub-ms cache hit latency; built-in WAF, DDoS, and bot protection; KV for edge-side rate limiting |
    42→| OpenSearch for search + CQRS | Full-text search across payments, transactions, and businesses; CDC sync from Kafka provides near-real-time read models |
    43→
    44→### 1.3 Key Metrics Targets
    45→
    46→| Metric | Target | Measurement |
    47→|--------|--------|-------------|
    48→| API p95 latency | **< 100ms** | Measured at Cloudflare edge → origin round-trip |
    49→| API p99 latency | **< 500ms** | Measured at application layer |
    50→| Availability | **99.99%** | Monthly uptime (52.56 min downtime/year max) |
    51→| Initial JS payload | **< 100KB** | Gzipped, measured by Web Vitals Lighthouse |
    52→| Time to Interactive (TTI) | **< 2.5s** | On 4G connection, median mobile device |
    53→| Payment completion time | **< 3s** | End-to-end from initiation to provider callback |
    54→| Kafka consumer lag | **< 1,000 messages** | Per consumer group, p99 |
    55→| RPO (Recovery Point Objective) | **< 1 minute** | Maximum acceptable data loss |
    56→| RTO (Recovery Time Objective) | **< 15 minutes** | Maximum acceptable downtime after disaster |
    57→| Cache hit ratio (L1) | **> 90%** | Cloudflare CDN hit ratio |
    58→| Cache hit ratio (L2) | **> 85%** | Redis cache hit ratio |
    59→
    60→### 1.4 Business Context
    61→
    62→Youngsend serves B2B clients (businesses and marketplaces) that need escrow-protected payments, multi-currency wallets, and trust verification for counterparties. The platform manages the full lifecycle: payment initiation through 5 provider integrations (Stripe, Paystack, Flutterwave, IntaSend, Paya), wallet operations (deposits, withdrawals, currency conversion), escrow transactions (create, fund, release, dispute, refund), and compliance (KYC, AML screening, fraud detection). Each tenant operates in complete isolation enforced at both the application and database layers via PostgreSQL Row Level Security (RLS).

   138→### 2.2 Request Flow: End-to-End
   139→
   140→The following diagram traces a typical user request from browser to database and back:
   141→
   142→```
   143→User (Browser)
   144→  │
   145→  │  1. DNS Lookup → Cloudflare Anycast
   146→  │  2. TCP/TLS to nearest PoP
   147→  ▼
   148→Cloudflare Edge (L1 Cache)
   149→  │
   150→  │  3. Edge Worker executes:
   151→  │     - Geo-blocking check
   152→  │     - Bot protection (User-Agent filter)
   153→  │     - Rate limiting (KV sliding window)
   154→  │     - JWT validation (RS256 crypto.subtle)
   155→  │     - Security headers injection
   156→  │     - A/B test variant injection
   157→  │
   158→  │  4. Cache check:
   159→  │     HIT  → Return cached response (X-Cache-Status: HIT)
   160→  │     MISS → Forward to origin
   161→  ▼
   162→Next.js Application (GKE Pod)
   163→  │
   164→  │  5. Route handler receives request
   165→  │     - Parse session/JWT
   166→  │     - Set tenant context (RLS)
   167→  │     - Check L2 Redis cache
   168→  │
   169→  │  6. Redis L2 check:
   170→  │     HIT  → Return cached data (X-Cache-Tier: L2-Redis)
   171→  │     MISS → Query database
   172→  ▼
   173→PostgreSQL / OpenSearch
   174→  │
   175→  │  7. Query execution:
   176→  │     - Read queries → Read Replica (PgBouncer Pool B)
   177→  │     - Write queries → Primary (PgBouncer Pool A)
   178→  │     - Search queries → OpenSearch
   179→  │
   180→  │  8. Response flows back:
   181→  │     - Write-through to Redis L2
   182→  │     - Response to client
   183→  ▼
   184→User (Browser)
   185→  │
   186→  │  9. Response received
   187→  │     - RSC HTML streamed (Suspense boundaries)
   188→  │     - JS chunks loaded on-demand (next/dynamic)
   189→  │     - Interactive hydration
   190→```

   192→### 2.3 Service Decomposition Strategy
   193→
   194→Youngsend adopts a **pragmatic monolith-first** approach with Kafka event boundaries. The current implementation uses Next.js App Router as a monolithic BFF that handles all API routes and server component rendering. However, all internal communication follows bounded-context patterns — each domain publishes events to its own Kafka topic namespace, enabling future extraction into independent microservices without architectural changes.
   195→
   196→The extraction path is:
   197→1. **Phase 1 (Current):** Monolithic Next.js BFF + Kafka event backbone
   198→2. **Phase 2:** Extract Payment and Wallet services (highest traffic, most independent)
   199→3. **Phase 3:** Extract Escrow, Trust, Fraud, Compliance services
   200→4. **Phase 4:** Extract Notification, Search, Analytics services
   201→
   202→Each extraction is a zero-downtime operation: the BFF continues to serve as a thin proxy/SSR layer while routing API calls to the newly extracted service.

   233→### 3.2 Service Catalog
   234→
   235→#### 3.2.1 API Gateway
   236→
   237→**Responsibility:** Single entry point for all client requests. Handles cross-cutting concerns: authentication validation, rate limiting, geo-blocking, bot protection, A/B testing, security header injection, and request routing. Implemented as a two-layer gateway: Cloudflare Edge Worker for L1 concerns (global, low-latency) and Next.js middleware for application-level concerns.
   238→
   239→**Tech Stack:**
   240→- Cloudflare Workers (V2 Isolates, KV for rate limiting state)
   241→- Next.js Middleware (route matching, session validation)
   242→- Wrangler CLI for deployment
   243→
   244→**Scaling Strategy:** Cloudflare Workers auto-scale to zero — no provisioning needed. Each request is processed at the nearest of 300+ PoPs. Next.js middleware runs in-process with the Next.js application and scales with the application pods.
   245→
   246→**Implementation Files:** `infra/cloudflare/worker.ts`, `infra/cloudflare/wrangler.toml`, `infra/cloudflare/cache-rules.json`, `infra/cloudflare/page-shield.json`
   247→
   248→---
   249→
   250→#### 3.2.2 Auth Service
   251→
   252→**Responsibility:** User authentication (sign-in, sign-up, password reset), session management, JWT issuance and validation, role-based access control (RBAC), multi-factor authentication, and OAuth provider integration. Currently implemented via NextAuth.js v5 with credentials provider; designed for extension to OAuth providers (Google, Microsoft) and passkey/WebAuthn support.
   253→
   254→**Tech Stack:**
   255→- NextAuth.js v5 (App Router integration)
   256→- JWT tokens (RS256 signed, stored in httpOnly cookies)
   257→- PostgreSQL `Account` table (user credentials, roles, status)
   258→- Redis (session cache, rate limiting on auth endpoints)
   259→- Prisma ORM (typed queries, migrations)
   260→
   261→**Scaling Strategy:** Stateless JWT validation at edge (Cloudflare Worker); session verification against Redis for active session management. HPA scales Next.js pods based on CPU utilization (50-80% target).
   262→
   263→**Security Notes:**
   264→- JWT RS256 with public key distributed to Cloudflare Edge for validation
   265→- httpOnly, secure, SameSite=Strict cookies
   266→- CSRF protection via NextAuth double-submit cookie pattern
   267→- Password hashing with bcrypt (cost factor 12)
   268→- Account lockout after 5 failed attempts (10-minute cooldown)
   269→
   270→---
   271→
   272→#### 3.2.3 Payment Service
   273→
   274→**Responsibility:** End-to-end payment lifecycle management across 5 payment providers (Stripe, Paystack, Flutterwave, IntaSend, Paya). Handles payment initiation, provider routing, webhook processing, status tracking, refunds, and reconciliation. Implements a state machine for payment flow control and saga pattern for distributed transactions.
   275→
   276→**Tech Stack:**
   277→- 5 provider SDKs (Stripe Node.js, Paystack Node, Flutterwave, IntaSend, Paya REST)
   278→- Kafka producer/consumer (payment.events.* topics, EOS Tier 1)
   279→- Saga orchestrator (state machine with compensating transactions)
   280→- PostgreSQL `PaymentIntent` + `PaymentTransaction` tables
   281→- OpenSearch (payment search index with CDC sync)
   282→- Redis (payment status cache, idempotency keys)
   283→
   284→**Scaling Strategy:** HPA based on request rate and payment queue depth. Kafka consumer group scales independently — additional consumer instances subscribe to payment topics during peak. Provider-specific connection pools prevent single-provider outages from affecting others.
   285→
   286→**State Machine:**
   287→```
   288→IDLE → INITIATED → PROCESSING → COMPLETED
   289→         │             │
   290→         ▼             ▼
   291→      CANCELLED      FAILED
   292→                        │
   293→                        ▼
   294→                     REFUNDED
   295→```
   296→
   297→**Idempotency:** Every payment intent has a unique `idempotencyKey`. Duplicate requests with the same key return the existing payment state without creating a new transaction. This is critical for handling network retries and browser double-submissions.
   298→
   299→---
   300→
   301→#### 3.2.4 Wallet Service
   302→
   303→**Responsibility:** Digital wallet management for multi-currency holdings. Handles deposits (from payment completions), withdrawals (to external accounts), currency conversions (with rate caching), balance tracking, and wallet lifecycle (create, freeze, unfreeze, close). Maintains an immutable transaction ledger via event sourcing.
   304→
   305→**Tech Stack:**
   306→- Kafka producer/consumer (wallet.events.* topics, EOS Tier 1)
   307→- PostgreSQL `Wallet` + `WalletTransaction` tables (partitioned by month)
   308→- Redis (balance cache with invalidation, rate limiting)
   309→- PgBouncer connection pooling for high-concurrency balance queries
   310→
   311→**Scaling Strategy:** Wallet operations are partitioned by `walletId` in Kafka (12 partitions), enabling parallel processing. Read-heavy balance queries are routed to PostgreSQL read replicas. Monthly partitioning ensures query performance remains constant regardless of total transaction volume.
   312→
   313→**Consistency Model:** Wallet debits use pessimistic locking (`SELECT ... FOR UPDATE`) on the primary to prevent double-spend. Credits are applied synchronously within the payment saga. The wallet balance cache is invalidated via Redis Pub/Sub on every mutation.
   314→
   315→---
   316→
   317→#### 3.2.5 Escrow Service
   318→
   319→**Responsibility:** Escrow transaction lifecycle management — the core business differentiator. Manages escrow creation, funding (from wallet or payment), milestone tracking, partial/full release, dispute handling, and refund. Supports buyer-seller relationships with trust verification.
   320→
   321→**Tech Stack:**
   322→- Kafka producer/consumer (escrow.events.* topics, EOS Tier 1)
   323→- Saga orchestrator (escrow-funded → payment-confirmed → escrow-released)
   324→- PostgreSQL `EscrowTransaction` + `EscrowAuditLog` tables
   325→- OpenSearch (escrow search index)
   326→
   327→**Scaling Strategy:** 8 Kafka partitions for escrow events. Escrow audit log is partitioned by month (12 partitions for 2025, auto-created for future months). Active escrow queries use partial indexes to only scan non-terminal states.
   328→
   329→**Audit Trail:** Every state transition creates an immutable `EscrowAuditLog` entry with full before/after state, actor, timestamp, and reason. This provides a complete regulatory audit trail without impacting query performance on the main escrow table.
   330→
   331→---
   332→
   333→#### 3.2.6 Trust Score Service
   334→
   335→**Responsibility:** Calculates and maintains trust scores for businesses based on payment history, escrow completion rate, dispute resolution, KYC verification status, and review submissions. Trust scores influence escrow terms, payment limits, and platform visibility.
   336→
   337→**Tech Stack:**
   338→- Kafka consumer (trust.events.* topics, EOS Tier 2)
   339→- Kafka producer (consumes escrow.events.escrow_released, wallet.events.*)
   340→- PostgreSQL `TrustScore` + `TrustReview` + `BusinessRelationship` tables
   341→- OpenSearch (trust.score.snapshots — compacted topic for CQRS)
   342→
   343→**Scaling Strategy:** Trust score computation is triggered by Kafka events and runs asynchronously. The scoring algorithm uses a weighted composite of factors recalculated on each relevant event. Scores are cached in Redis with 10-minute TTL and invalidated on updates.
   344→
   345→---
   346→
   347→#### 3.2.7 Fraud Detection Service
   348→
   349→**Responsibility:** Real-time fraud detection using configurable rules and patterns. Monitors payment velocity, amount anomalies, geographic inconsistencies, device fingerprinting, and behavioral patterns. Generates fraud alerts, manages investigation cases, and can auto-block suspicious transactions.
   350→
   351→**Tech Stack:**
   352→- Kafka consumer (fraud.events.* + payment.events.payment_initiated, EOS Tier 2)
   353→- PostgreSQL `FraudAlert` + `FraudCase` + `FraudRule` tables
   354→- Redis (active fraud rules cache, 5-minute TTL)
   355→- GIN indexes on `FraudRule.condition` (JSONB) for rule pattern matching
   356→
   357→**Scaling Strategy:** Fraud rules are cached in Redis and evaluated in-memory for sub-millisecond decision latency. High-severity alerts trigger immediate PagerDuty escalation via the Alertmanager routing tree. Fraud alert spikes (>10 in 5 minutes) trigger automated investigation workflows.
   358→
   359→**Rule Engine:** Fraud rules are stored as JSONB conditions in PostgreSQL with GIN indexes for fast pattern matching. Rules support:
   360→- Amount thresholds (absolute and velocity-based)
   361→- Geographic anomalies (country mismatch, distance-based)
   362→- Device fingerprinting (new device, device rotation)
   363→- Behavioral patterns (time-of-day, frequency, session patterns)
   364→
   365→---
   366→
   367→#### 3.2.8 Compliance/KYC Service
   368→
   369→**Responsibility:** Regulatory compliance management including KYC document verification, AML screening against sanctions lists (OFAC, EU, local), PEP (Politically Exposed Person) checks, ongoing monitoring, and audit reporting. Manages compliance screenings, KYC submissions, and verification workflows.
   370→
   371→**Tech Stack:**
   372→- Kafka consumer (compliance.events.* topics, EOS Tier 2)
   373→- External API integrations (sanctions screening providers, document verification APIs)
   374→- PostgreSQL `ComplianceScreening` + `KYCSubmission` tables
   375→- OpenSearch (compliance search, audit trail)
   376→
   377→**Scaling Strategy:** KYC submissions are event-driven and processed asynchronously. Screening requests are batched for external API calls (rate limit management). Results are cached in OpenSearch for fast lookups and regulatory reporting.
   378→

   380→
   381→#### 3.2.9 Search Service (OpenSearch)
   382→
   383→**Responsibility:** Full-text search across payments, transactions, businesses, users, and audit logs. Provides faceted navigation, aggregations, autocomplete, and cross-index global search. Serves as the CQRS read model, synchronized from PostgreSQL via Kafka CDC.
   384→
   385→**Tech Stack:**
   386→- OpenSearch cluster (3 primary + 1 replica shards per index)
   387→- Kafka CDC consumer (subscribes to all domain events)
   388→- Custom HTTP REST client (no native driver dependency)
   389→- In-memory fallback store (Map-based, auto-activated when OpenSearch unavailable)
   390→

   496→### 4.2 PostgreSQL Architecture
   497→
   498→**Topology:** Primary + 2 synchronous read replicas managed by Patroni for high availability. A third async replica serves analytics/reporting workloads.
   499→
   500→**Connection Pooling:** PgBouncer in transaction mode handles up to 10,000 client connections multiplexed onto 160 server connections per pool. Three pools are configured:
   501→- **Pool A (WRITE):** Routes all INSERT/UPDATE/DELETE and SELECT FOR UPDATE to primary
   502→- **Pool B (READ):** Routes read-only queries to synchronous replica (lag < 100ms)
   503→- **Pool C (ANALYTICS):** Routes long-running analytics queries to async replica
   504→
   505→**Multi-Tenancy:** PostgreSQL Row Level Security (RLS) enforces tenant isolation at the database level across 30+ tenant-scoped tables. The application sets `app.tenant_id` as a session variable before every query:
   506→
   507→```sql
   508→SET LOCAL app.tenant_id = 'clx...';
   509→-- RLS policy automatically filters all queries to this tenant
   510→```
   511→
   512→**Partitioning Strategy:** Four high-volume tables use monthly RANGE partitioning:
   513→
   514→| Table | Estimated Rows/Year | Partitions | Benefit |
   515→|-------|--------------------|------------|---------|
   516→| `WalletTransaction` | 100M+ | 12/month | Query pruning by date, parallel scan |
   517→| `EscrowAuditLog` | 50M+ | 12/month | Easy archival of old records |
   518→| `Notification` | 500M+ | 12/month | Partition pruning for unread queries |
   519→| `PaymentTransaction` | 50M+ | 12/month | Maintenance per-partition (VACUUM/REINDEX) |
   520→
   521→**Index Strategy (for 100M users):**
   522→
   523→| Index Type | Count | Use Case |
   524→|------------|-------|----------|
   525→| B-tree (default) | 100+ | Primary keys, foreign keys, unique constraints |
   526→| Partial indexes | 25+ | Active/open records only (e.g., escrow WHERE status NOT IN ('completed')) |
   527→| Covering indexes | 18 | Index-only scans for dashboard APIs (INCLUDE columns) |
   528→| BRIN | 4 | Time-series tables (WalletTransaction, EscrowAuditLog) — 99% smaller than B-tree |
   529→| GIN | 11 | Full-text search, JSONB containment queries |
   530→| Composite | 20+ | Multi-column query patterns (business relationships, fraud severity) |
   531→
   532→**Type Optimizations (SQLite → PostgreSQL migration):**
   533→- `Float` → `Decimal` (exact precision for financial amounts)
   534→- `String` → `JSONB` (native operations, GIN indexing for metadata)
   535→- `String` enum fields → PostgreSQL native `ENUM` types
   536→- `String` email → `CITEXT` extension (case-insensitive without LOWER())
   537→
   538→**Backup & Recovery:**
   539→- Daily base backup at 02:00 UTC via `pg_basebackup`
   540→- Continuous WAL archiving to GCS
   541→- Point-in-Time Recovery: any second within 90-day retention
   542→- RPO: < 1 minute (synchronous replication to Replica B)
   543→- RTO: < 15 minutes (automated PITR from latest backup + WAL)
   544→- Weekly automated restore verification to staging

   546→### 4.3 Redis Architecture
   547→
   548→**Deployment:** 3-node Redis Sentinel cluster (Redis 7.2) with automatic failover. Deployed as a StatefulSet in GKE with persistent volumes.
   549→
   550→**Key Responsibilities:**
   551→1. **Application Caching:** Dashboard stats (30s TTL), exchange rates (60s TTL), user profiles (5m TTL), payment methods (10m TTL), fraud rules (5m TTL)
   552→2. **Rate Limiting:** Sliding window counters per endpoint category (global 300/min, auth 10/min, payment 30/min)
   553→3. **Session Cache:** Active session state with 30-minute TTL

   628→## 5. Event-Driven Architecture
   629→
   630→### 5.1 Design Principles
   631→
   632→Youngsend's event-driven architecture is built on four core principles:
   633→
   634→1. **Events as the source of truth:** Every state mutation publishes an immutable event to Kafka. Services read events to build their own materialized views rather than sharing databases.
   635→2. **Loose coupling via topics:** Services communicate exclusively through Kafka topics. No direct service-to-service calls for domain operations. This enables independent deployment, scaling, and schema evolution.
   636→3. **Bounded context isolation:** Each domain owns its topic namespace (`<domain>.events.<event-type>`). Events cross domain boundaries through consumer subscriptions, not direct calls.
   637→4. **Eventual consistency:** The system is designed for eventual consistency. Read models in OpenSearch may lag behind the primary PostgreSQL store by a few seconds. Financial operations (payment, wallet) use synchronous flows within the saga; non-critical updates (trust scores, notifications) are fully asynchronous.
   638→

   709→            │  │ WALLET   │   └──────────┘                    │

   741→| Step | Forward Action | Compensating Action | Priority |

   743→| Wallet Debit | Debit wallet for payment amount | Credit wallet (refund) | Critical |
   744→| Escrow Create | Create escrow holding | Cancel escrow | Critical |

   747→### 5.4 Event Sourcing for Audit
   748→
   749→The `audit.events.audit_action_logged` topic serves as an immutable, append-only event log capturing every significant action across the platform. Every domain event is also consumed by the audit service, which creates a canonical audit entry with:
   750→
   751→- `eventId` — Unique UUID (prevents duplicate processing)
   752→- `correlationId` — Links all events in a business transaction
   753→- `causationId` — Chain of events (parent → child)
   754→- `actor` — Who performed the action (userId or system)
   755→- `action` — What was done (create, update, delete, status_change)
   756→- `resource` — What was affected (entity type + ID)
   757→- `before/after` — Full state snapshot for compliance
   758→- `ipAddress` — Client IP for forensic analysis
   759→- `timestamp` — UTC ISO 8601
   760→
   761→The audit topic has 90-day retention with 12 partitions and EOS Tier 3 (fire-and-forget). Audit entries are also indexed in OpenSearch for fast compliance searches.
   762→
   763→### 5.5 CQRS Read Models via OpenSearch
   764→
   765→The CQRS (Command Query Responsibility Segregation) pattern separates write operations (PostgreSQL) from read operations (OpenSearch). Write operations produce Kafka events; the OpenSearch CDC consumer projects these events into optimized read models.
   766→
   767→**Benefits:**
   768→- Read queries don't impact OLTP performance on PostgreSQL
   769→- OpenSearch supports full-text search, aggregations, and faceted navigation
   770→- Read models can be optimized independently (different indexing, denormalization)
   771→- Eventual consistency is acceptable for search/use-facing queries
   772→
   773→**Sync Strategies:**
   774→1. **CDC (primary):** Kafka consumer subscribes to all domain events and translates them into OpenSearch index/delete operations
   775→2. **Single-entity sync:** Used in API routes after CRUD operations for near-real-time updates
   776→3. **Bulk sync:** Cursor-based reindexing for initial setup or full rebuilds
   777→
   778→### 5.6 Consumer Group Strategy
   779→
   780→**Naming Convention:** `<owning-service>.<domain>.consumer`
   781→
   782→| Consumer Group | Subscribed Topics | EOS Tier |
   783→|-----------------|-------------------|----------|
   784→| `wallet-service.payment.consumer` | payment.events.payment_completed, payment_refunded | Tier 1 |
   785→| `escrow-service.payment.consumer` | payment.events.payment_completed | Tier 1 |
   786→| `notification-service.*.consumer` | All *.events.* (fan-out) | Tier 3 |
   787→| `trust-service.escrow.consumer` | escrow.events.escrow_released | Tier 2 |
   788→| `fraud-engine.payment.consumer` | payment.events.payment_initiated, payment_processing | Tier 2 |
   789→| `compliance-service.payment.consumer` | payment.events.payment_initiated | Tier 2 |
   790→| `audit-service.*.consumer` | All *.events.* (append-only log) | Tier 3 |
   791→| `search-service.*.consumer` | All *.events.* (CDC sync) | Tier 2 |
   792→
   793→**Assignment:** Cooperative-sticky partition assignment ensures minimal rebalancing disruption. One consumer group per service-domain pair prevents cross-domain coupling. `max.poll.records` is tuned per domain (lower for payment, higher for audit).

   797→## 6. Caching Strategy
   798→
   799→### 6.1 Three-Tier Cache Hierarchy
   800→
   801→Youngsend employs a three-tier cache hierarchy designed to serve the vast majority of requests without hitting the origin database. Each tier has progressively lower latency but higher staleness tolerance.
   802→
   803→```
   804→┌─────────────────────────────────────────────────────────────────────────┐
   805→│                          CACHE ARCHITECTURE                              │
   806→│                                                                          │
   807→│  TIER 1: Cloudflare CDN (Global Edge, 300+ PoPs)                       │
   808→│  ┌─────────────────────────────────────────────────────────────────┐    │
   809→│  │  Latency: < 5ms (cache hit)                                     │    │
   810→│  │  Static assets: 1 year TTL (immutable, content-hashed)          │    │
   811→│  │  Public APIs: 30s-10min TTL with SWR                            │    │
   812→│  │  Cache key: Path + Query + Auth identity                       │    │
   813→│  │  Invalidation: Surrogate keys, URL purge, prefix purge           │    │
   814→│  │  Hit ratio target: > 90%                                       │    │
   815→│  └─────────────────────────────────────────────────────────────────┘    │
   816→│                              │ MISS                                       │
   817→│                              ▼                                            │
   818→│  TIER 2: Redis (In-Cluster, Sentinel HA)                                 │
   819→│  ┌─────────────────────────────────────────────────────────────────┐    │
   820→│  │  Latency: < 1ms (cache hit)                                     │    │
   821→│  │  Dashboard stats: 30s TTL + 60s SWR                              │    │
   822→│  │  Exchange rates: 60s TTL + 5min SWR                              │    │
   823→│  │  User profiles: 5min TTL + 10min SWR                             │    │
   824→│  │  Fraud rules: 5min TTL + 10min SWR                               │    │
   825→│  │  Rate limits: 1min sliding window                                │    │
   826→│  │  Invalidation: Pub/Sub, tag-based                                 │    │
   827→│  │  Stampede protection: Distributed lock (SET NX EX)               │    │
   828→│  │  Hit ratio target: > 85%                                         │    │
   829→│  └─────────────────────────────────────────────────────────────────┘    │
   830→│                              │ MISS                                       │
   831→│                              ▼                                            │
   832→│  TIER 3: Origin (Next.js Application → PostgreSQL)                       │
   833→│  ┌─────────────────────────────────────────────────────────────────┐    │
   834→│  │  Latency: 10-100ms (typical)                                     │    │
   835→│  │  Full request processing through Next.js                         │    │
   836→│  │  Read replica routing for SELECT queries                          │    │
   837→│  │  RSC streaming for progressive HTML delivery                      │    │
   838→│  │  Write-through: Response cached in L2 on return                   │    │
   839→│  │  Surrogate-Key header set for L1 cacheability                    │    │
   840→│  └─────────────────────────────────────────────────────────────────┘    │
   841→└─────────────────────────────────────────────────────────────────────────┘
   842→```

   844→### 6.2 Per-Endpoint Caching Strategy
   845→
   846→#### L1: Cloudflare CDN Cache Rules
   847→
   848→| Resource | Strategy | Edge TTL | Browser TTL | SWR | Cache Key |
   849→|----------|----------|----------|-------------|-----|-----------|
   850→| `/_next/static/*` | Cache-first, immutable | 1 year | 1 year | 1 day | Path only |
   851→| `/public/*.{png,jpg,svg}` | Cache-first | 1 month | 1 month | 1 day | Path only |
   852→| `/api/dashboard/stats` | Stale-while-revalidate | 30s | 0s | 60s | Path + query + auth |
   853→| `/api/currency` | Stale-while-revalidate | 60s | 0s | 120s | Path + query |
   854→| `/api/wallets/rates` | Stale-while-revalidate | 60s | 0s | 120s | Path + query |
   855→| `/api/payment-methods/global` | Stale-while-revalidate | 10 min | 0s | 20 min | Path + query |
   856→| `/api/auth/*` | **Bypass** | — | — | — | — |
   857→| `/api/payments/*` | **Bypass** | — | — | — | — |
   858→| All POST/PUT/DELETE | **Bypass** | — | — | — | — |
   859→
   860→#### L2: Redis Cache Rules
   861→
   862→| Cache Key Pattern | TTL | SWR Grace | Tags | Notes |
   863→|-------------------|-----|-----------|------|-------|
   864→| `ys:dash:{tenantId}:{role}` | 30s | 60s | `dash:{tenantId}` | Dashboard stats aggregation |
   865→| `ys:fx:*` | 60s | 5 min | `currency` | Exchange rates |
   866→| `ys:pm:{tenantId}:{currency}` | 10 min | 20 min | `pm:{tenantId}` | Payment methods per tenant |
   867→| `ys:u:{userId}` | 5 min | 10 min | `user:{userId}` | User profile |
   868→| `ys:fr:{tenantId}:{type}` | 5 min | 10 min | `fraud:{tenantId}` | Active fraud rules |
   869→| `ys:sess:{userId}:{device}` | 30 min | 0 | `session:{userId}` | Session state |
   870→| `ys:rl:{key}:{window}` | 1 min | 0 | — | Rate limiting counters |
   871→| `ys:lock:{key}` | 5s | 0 | — | Stampede protection lock |
   872→
   873→### 6.3 Cache Invalidation Patterns
   874→
   875→**Tag-Based Invalidation (L1 — Cloudflare):**
   876→Each cached response includes `Surrogate-Key` headers. The Cloudflare API supports purging by tag:
   877→```bash
   878→# Purge all dashboard stats for a specific tenant
   879→curl -X POST "https://api.cloudflare.com/client/v4/zones/{zone}/purge_tags" \
   880→  -H "Authorization: Bearer $CF_TOKEN" \
   881→  -d '{"tags":["dash:t123"]}'
   882→```
   883→
   884→**URL-Based Invalidation (L1):**
   885→```bash
   886→# Purge specific API response
   887→curl -X POST "https://api.cloudflare.com/client/v4/zones/{zone}/purge_url" \
   888→  -d '{"urls":["https://youngsend.com/api/currency?base=NGN"]}'
   889→```
   890→
   891→**Redis Pub/Sub Invalidation (L2):**
   892→When the origin mutates data, invalidation events are published:
   893→```
   894→PUBLISH cache:invalidate:dash {"prefix":"ys:dash:", "tags":["dash:t123"]}
   895→# All Redis instances receive and flush matching keys
   896→```
   897→
   898→**Write-Through (L2 → L1):**
   899→API responses include `Surrogate-Key` headers that Cloudflare uses for subsequent tag-based purges. The origin always sets fresh cache values in Redis before returning the response, ensuring subsequent requests hit L2.
   900→
   901→### 6.4 Cache Stampede Protection
   902→
   903→When a hot cache key expires and multiple requests attempt to populate it simultaneously, stampede protection prevents redundant origin hits:
   904→
   905→1. **Distributed Lock:** First request acquires a lock via `SET NX EX 5` on `ys:lock:{key}`
   906→2. **Single Origin Hit:** Only the lock holder queries the origin
   907→3. **Stale Data for Others:** Concurrent requests receive stale data (SWR grace period) or wait for the lock holder
   908→4. **Lock Release:** Lock automatically expires after 5 seconds (failsafe)
   909→5. **Cache Populate:** Lock holder writes fresh data to Redis with full TTL
   910→
   911→This pattern ensures that even during cache expiry events, the origin only receives one request per cache key, regardless of concurrent access.

   915→## 7. Performance Optimization
   916→
   917→### 7.1 React Server Components (RSC) + Streaming SSR
   918→
   919→Youngsend's frontend performance strategy is centered on RSC and streaming SSR, which fundamentally changes how the application delivers content to the browser.
   920→
   921→**Architecture:**
   922→- `page.tsx` is a 22-line Server Component (was 317-line client monolith)
   923→- All 12 dashboard tabs (2,947 lines total) loaded on-demand via `next/dynamic` with `ssr: false`
   924→- Active tab wrapped in Suspense boundary for streaming SSR
   925→- `DashboardShell.tsx` renders skeleton fallbacks while tabs load
   926→
   927→**Impact:**
   928→- Initial JS payload reduced from ~2MB+ to ~50-80KB (shell + active tab only)
   929→- Heavy dependencies (recharts, framer-motion, lodash) only loaded when their tab is active
   930→- Server-rendered HTML streams progressively — user sees content before all JS loads
   931→- Time to First Byte (TTFB) under 200ms for cached pages
   932→
   933→```typescript
   934→// Example: Lazy-loaded tab with skeleton fallback
   935→const EscrowTab = dynamic(() => import('./tabs/EscrowTab'), {
   936→  loading: () => <EscrowSkeleton />,
   937→  ssr: false,
   938→});
   939→```
   940→
   941→### 7.2 Bundle Optimization Targets
   942→
   943→**Bundle Budgets:**
   944→
   945→| Chunk Category | Max Size (gzipped) | Strategy |
   946→|----------------|-------------------|----------|
   947→| Initial HTML (RSC) | < 50KB | Server-rendered, no JS required |
   948→| First Load JS (shared) | < 100KB | Core framework + router |
   949→| Per-Tab JS | < 80KB | Code-split via next/dynamic |
   950→| Total page JS (worst case) | < 200KB | With lazy loading, rarely hit |
   951→
   952→**Optimization Techniques:**
   953→1. **Code Splitting:** Each dashboard tab is a separate chunk loaded on-demand
   954→2. **Tree Shaking:** ES modules + Next.js automatic tree shaking eliminates unused exports
   955→3. **Dynamic Imports:** Heavy libraries (recharts, framer-motion) only imported in their tab
   956→4. **Image Optimization:** Next.js Image component with automatic WebP/AVIF conversion
   957→5. **Font Optimization:** `next/font` with font-display: swap, preloaded
   958→
   959→### 7.3 CDN and Edge Optimization
   960→
   961→1. **Immutable Static Assets:** `/_next/static/*` uses content-hash filenames with 1-year cache. Cache-busting handled by build-time hash changes.
   962→2. **Preconnect/Preload:** Critical origins (API endpoints, fonts) use `<link rel="preconnect">` to eliminate connection setup latency.
   963→3. **HTTP/2 + HTTP/3:** Cloudflare automatically multiplexes requests over HTTP/2. HTTP/3 (QUIC) available on modern browsers for faster connection establishment.
   964→4. **Brotli Compression:** Cloudflare serves Brotli-compressed responses (better than gzip) for supported clients.
   965→5. **Early Hints:** Cloudflare can send 103 Early Hints for critical resources while the origin prepares the response.
   966→
   967→### 7.4 Connection Pooling and Query Optimization
   968→
   969→**PostgreSQL via PgBouncer:**
   970→- Transaction mode: Server connections held only during transaction (~5-50ms)
   971→- Pool size: `(core_count * 2) + spindle_count = 160` for a 64-core machine
   972→- Max client connections: 10,000 (from all Next.js pods)
   973→- Prisma connection_limit: 1 per pod (PgBouncer handles multiplexing)
   974→
   975→**Query Optimization:**
   976→1. **Read Replica Routing:** All `SELECT` queries (within explicit read transactions) route to synchronous replica
   977→2. **Partial Indexes:** Dashboard queries only scan active/non-terminal records
   978→3. **Covering Indexes:** Index-only scans return data without hitting the heap (INCLUDE columns)
   979→4. **Partition Pruning:** Monthly partitions ensure queries only scan relevant months
   980→5. **BRIN Indexes:** Time-series tables use block-range indexes (99% smaller than B-tree)
   981→6. **Query Plan Caching:** Prisma caches prepared statements; PostgreSQL uses plan cache for repeated queries
   982→7. **Slow Query Logging:** `log_min_duration_statement = 500ms` captures queries exceeding 500ms for optimization
   983→
   984→**Redis Optimization:**
   985→- Pipeline multiple commands to reduce round trips
   986→- Connection pooling with `ioredis` (cluster mode with Sentinel)
   987→- Lua scripting for atomic multi-key operations (rate limiting, stampede protection)

  1043→### 8.2 Authentication
  1044→
  1045→**JWT + Session Architecture:**
  1046→- NextAuth.js v5 manages authentication with credentials provider
  1047→- JWTs signed with RS256 (RSA-SHA256) — public key distributed to Cloudflare Edge for validation
  1048→- Short-lived access tokens (15-minute expiry) with refresh token rotation
  1049→- Session stored in httpOnly, Secure, SameSite=Strict cookies
  1050→- JWT payload includes: `sub` (userId), `email`, `role`, `tenantId`, `exp`, `iat`
  1051→
  1052→**Edge Validation (Cloudflare Worker):**
  1053→- RSA signature verification using Web Crypto API (`crypto.subtle.verify`)
  1054→- Expiration (`exp`) and not-before (`nbf`) checks
  1055→- **Fail-open design:** If edge validation encounters an error, request passes to origin for reliability
  1056→- Public endpoints (login, signup, health) bypass JWT validation
  1057→
  1058→**Password Security:**
  1059→- bcrypt hashing with cost factor 12 (~250ms per hash)
  1060→- Account lockout after 5 failed attempts (10-minute cooldown via Redis)
  1061→- Password policy enforcement (minimum 12 characters, mixed case, numbers)
  1062→
  1063→### 8.3 Authorization
  1064→
  1065→**Role-Based Access Control (RBAC):**
  1066→Five roles defined at the PostgreSQL ENUM level:
  1067→- `admin` — Full platform access, tenant management
  1068→- `buyer` — Create escrow, initiate payments, manage own profile
  1069→- `seller` — Accept escrow, receive payments, manage own business
  1070→- `auditor` — Read-only access to audit logs and compliance reports
  1071→- `viewer` — Read-only dashboard access
  1072→
  1073→**Row Level Security (RLS):**
  1074→Every tenant-scoped table enforces RLS via PostgreSQL policies:
  1075→```sql
  1076→ALTER TABLE "Account" ENABLE ROW LEVEL SECURITY;
  1077→CREATE POLICY tenant_isolation ON "Account"
  1078→  USING (tenant_id = current_setting('app.tenant_id', true));
  1079→```
  1080→The application sets `app.tenant_id` at connection/session level before every query. RLS is enforced at the database engine level — even if application code has a bug, cross-tenant data leakage is impossible.
  1081→
  1082→### 8.4 Encryption
  1083→
  1084→**At Rest:**
  1085→- PostgreSQL: AES-256-GCM encryption via GCE-managed encryption keys (CMEK)
  1086→- Redis: In-transit encryption only (data classified as cacheable/non-sensitive)
  1087→- GCS backups: Server-side encryption with Google-managed keys
  1088→- K8s Secrets: etcd encryption enabled (AES-CBC)
  1089→
  1090→**In Transit:**
  1091→- TLS 1.2+ minimum (TLS 1.3 preferred)
  1092→- Cloudflare → Origin: TLS with Cloudflare origin certificates
  1093→- Internal service communication: mTLS via Istio service mesh (future)
  1094→- Database connections: SSL mode `require` with certificate verification
  1095→
  1096→### 8.5 PCI DSS Compliance
  1097→
  1098→Youngsend does not store cardholder data — all payment processing is delegated to PCI-compliant providers (Stripe, Paystack, Flutterwave, IntaSend, Paya). However, the platform implements PCI DSS best practices:
  1099→- No storage of full card numbers, CVV, or expiration dates
  1100→- Payment provider tokens used for reference (not raw card data)
  1101→- All payment pages served over HTTPS with strict CSP
  1102→- Access to payment-related audit logs restricted to admin and auditor roles
  1103→- Quarterly access reviews for payment system components
  1104→
  1105→### 8.6 Idempotent Payments
  1106→
  1107→Every payment intent includes a unique `idempotencyKey` (UUID v4). The payment service checks for existing intents with the same key before creating a new one:
  1108→- **Duplicate request:** Returns existing payment state (no new charge)
  1109→- **Network retry:** Provider SDKs use provider-level idempotency keys
  1110→- **Kafka producer:** Idempotent producer (`enable.idempotence=true`) prevents duplicate events on retry
  1111→- **Saga orchestrator:** Deduplication by `eventId` + `correlationId`
  1112→
  1113→### 8.7 Rate Limiting
  1114→
  1115→Multi-layer rate limiting enforced at edge (Cloudflare KV) and application (Redis):
  1116→
  1117→| Category | Max Requests | Window | Enforcement Layer |
  1118→|----------|-------------|--------|-------------------|
  1119→| Global | 300/min | 60s | Cloudflare KV (sliding window) |
  1120→| Auth | 10/min | 60s | Cloudflare + Redis |
  1121→| API | 100/min | 60s | Redis (per-user, per-tenant) |
  1122→| Payment | 30/min | 60s | Redis (per-user) |
  1123→| Webhook | 1000/min | 60s | Cloudflare (per-provider) |
  1124→| Static | 600/min | 60s | Cloudflare |
  1125→
  1126→Rate limit headers are included in every response: `X-RateLimit-Limit`, `X-RateLimit-Remaining`, `X-RateLimit-Reset`.
  1127→
  1128→### 8.8 Security Headers
  1129→
  1130→Enforced at both Cloudflare Edge and Next.js middleware:
  1131→- `Content-Security-Policy`: Strict CSP with nonce support, inline scripts disabled, allowlisted connections (Stripe, Paystack, Flutterwave, IntaSend, Paya)
  1132→- `Strict-Transport-Security`: `max-age=63072000; includeSubDomains; preload`
  1133→- `X-Frame-Options`: DENY (prevents clickjacking)
  1134→- `X-Content-Type-Options`: nosniff
  1135→- `Referrer-Policy`: strict-origin-when-cross-origin
  1136→- `Permissions-Policy`: Restricts browser features (camera, microphone, geolocation)
  1137→
  1138→CSP violations reported to `/api/security/csp-report` for monitoring.

  1276→### 10.1 Kubernetes Architecture (GKE)
  1277→
  1278→**Cluster Configuration:**
  1279→- **Provider:** Google Kubernetes Engine (GKE) on GCP
  1280→- **Version:** Latest stable via REGULAR release channel
  1281→- **Type:** Private cluster (no public endpoints, private nodes)
  1282→- **Networking:** VPC with custom subnets, separate pod/service CIDR ranges
  1283→- **Node Pools:** 3 dedicated pools with autoscaling
  1284→
  1285→| Node Pool | Machine Type | Min | Max | Disk | Purpose |
  1286→|-----------|-------------|-----|-----|------|---------|
  1287→| `frontend` | e2-highcpu-4 (spot) | 3 | 100 | 50GB pd-standard | Next.js pods |
  1288→| `backend` | e2-highmem-4 | 3 | 50 | 100GB pd-ssd | Microservices (future) |
  1289→| `data` | n2-highmem-8 | 3 | 20 | 500GB pd-ssd | PostgreSQL, Kafka, Redis |
  1290→
  1291→**Workload Placement:**
  1292→- Data-layer workloads (PostgreSQL, Kafka, Redis) scheduled on `data` node pool via taint toleration (`node-role=data:NoSchedule`)
  1293→- Next.js pods scheduled on `frontend` pool (spot instances for cost optimization)
  1294→- Topology spread constraints ensure pods are distributed across zones and hosts
  1295→
  1296→**Next.js Deployment:**
  1297→- 3 replicas minimum (rolling update strategy: maxSurge=1, maxUnavailable=0)
  1298→- Init container runs `prisma migrate deploy` before application starts
  1299→- Resource requests: 256Mi/250m CPU; limits: 512Mi/500m CPU
  1300→- Liveness probe: `/api/health` (15s period, 3 failure threshold)
  1301→- Readiness probe: `/api/ready` (10s period, 3 failure threshold)
  1302→- Startup probe: `/api/health` (5s period, 12 failure threshold = 60s max startup)
  1303→- `NODE_OPTIONS: --max-old-space-size=384` for memory stability
  1304→- `/tmp` (100Mi) and `.next/cache` (256Mi) as `emptyDir` volumes
  1305→- Security context: runAsNonRoot, readOnlyRootFilesystem, drop ALL capabilities

  1373→### 10.5 Disaster Recovery
  1374→
  1375→| Scenario | RTO | RPO | Procedure |
  1376→|----------|-----|-----|-----------|
  1377→| Single pod failure | 0s (automatic) | 0s | K8s auto-heals via replica set; HPA scales replacement |
  1378→| Node pool failure | < 2min | 0s | MIG auto-heals; pods rescheduled to healthy nodes |
  1379→| PostgreSQL primary failure | < 30s | < 1min | Patroni automatic failover to sync replica |
  1380→| Redis primary failure | < 10s | < 1s | Sentinel automatic failover to replica |
  1381→| Kafka broker failure | 0s (automatic) | 0s | Replication factor 3 ensures no data loss |
  1382→| Cloudflare outage | < 5min | 0s | DNS failover to direct GKE ingress (manual) |
  1383→| Full cluster failure | < 15min | < 1min | Restore from PITR backup in new cluster |
  1384→| Region failure | < 1 hour | < 5min | Cross-region DR cluster (future, warm standby) |

  1386→### 10.6 Cost Optimization
  1387→
  1388→**Compute:**
  1389→- Spot instances for frontend node pool (up to 90% savings vs on-demand)
  1390→- Autoscaling (min 3, max 100) ensures no over-provisioning
  1391→- Right-sizing: e2-highcpu-4 for Next.js (CPU-bound), e2-highmem-4 for backend (memory-bound)
  1392→
  1393→**Database:**
  1394→- PgBouncer reduces PostgreSQL connection overhead (160 server connections serve 10,000 clients)
  1395→- Read replica offloading reduces primary load by ~60%
  1396→- Monthly partition archival detaches old data to cold storage (lower storage costs)
  1397→
  1398→**Caching:**
  1399→- 3-tier cache hierarchy: ~95% of reads served from cache, reducing database load
  1400→- Redis allkeys-lru eviction prevents unbounded memory growth
  1401→
  1402→**Networking:**
  1403→- Private GKE cluster with Cloudflare as entry point eliminates NAT gateway costs
  1404→- Internal traffic uses pod-to-pod communication (no external egress charges)

  1587→## Appendix B: Glossary
  1588→
  1589→| Term | Definition |
  1590→|------|-----------|
  1591→| BFF | Backend for Frontend — an application layer that serves as the API backend for a specific frontend |
  1592→| BRIN | Block Range Index — PostgreSQL index type optimized for physically ordered data |
  1593→| CDC | Change Data Capture — pattern for tracking data changes in a database and propagating them |
  1594→| CQRS | Command Query Responsibility Segregation — separate read and write models |
  1595→| DLQ | Dead Letter Queue — queue for messages that failed processing after all retries |
  1596→| EOS | Exactly-Once Semantics — guarantee that each message is processed exactly once |
  1597→| GIN | Generalized Inverted Index — PostgreSQL index type for full-text and JSONB |
  1598→| HPA | Horizontal Pod Autoscaler — Kubernetes controller that adjusts replica count |
  1599→| MIG | Managed Instance Group — GCP auto-healing group of VMs |
  1600→| OTel | OpenTelemetry — open-source observability framework |
  1601→| PITR | Point-in-Time Recovery — ability to restore database to any moment in time |
  1602→| PoP | Point of Presence — physical location where CDN nodes are deployed |
  1603→| RBC | Row Level Security — PostgreSQL feature for row-level access control |
  1604→| RSC | React Server Components — React components rendered on the server |
  1605→| RPO | Recovery Point Objective — maximum acceptable data loss duration |
  1606→| RTO | Recovery Time Objective — maximum acceptable downtime duration |
  1607→| SLI | Service Level Indicator — quantitative measure of service behavior |
